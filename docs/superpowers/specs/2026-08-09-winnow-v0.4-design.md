# Winnow v0.4 — Reach and Proof

Date: 2026-08-09
Status: approved for planning

## Why this release exists

v0.3.0 is live on the Chrome Web Store (published 2026-08-02, 37.45 KiB, permission
`storage`). The engine is in good shape: ten signals, 390 tests, calibration against
roughly thirty real listings, and a set of refusals — `null` adjusted ratings, skipped
checks, ratings-only states — that are the reason to trust it at all.

None of that is reaching anyone. The listing has **zero ratings** and an install count too
low for the store to display. A competitor launched into the identical position — A–F
grade, six signals, on-page, no affiliate links, "transparent reasoning" — and sits at
**501 users and 3.8 stars**, on the strength of a search-optimised content operation rather
than a better engine.

So v0.4 is not about making the analysis smarter. It is about three things:

1. **Being present where people shop.** Winnow only works on `/dp/` pages. Shopping starts
   on a search results page, and the feature Fakespot users most often describe missing is
   grades on the search grid.
2. **Being available where the orphaned users are.** Fakespot was Mozilla's. Its ten
   million displaced users skew Firefox, and Winnow is Chrome-only.
3. **Saying the one true thing nobody else can say.** The competitor's own store listing
   declares that it handles *personally identifiable information and authentication
   information*. Winnow's declares `storage`. That difference is attested by Google on both
   listings, it is verifiable in thirty seconds, and Winnow currently mentions it nowhere.

## Scope

In scope for v0.4:

- A marketplace registry that becomes the single source of truth for storefronts.
- Search-results-page badges, backed by a local cache of grades already earned.
- Six additional storefronts.
- A Firefox build target and AMO package.
- Trust-proof copy in the panel, the options page, and the store listing.

Explicitly **out** of scope: landing site deployment and store-listing rework (deferred to a
separate distribution effort), new scoring signals, any server work, any monetisation.

## Non-negotiables this design must not break

These are pre-existing commitments. Every decision below was checked against them.

- No network requests from the shipped build. No telemetry. No affiliate links, ever.
- **Never crawl using the user's Amazon session.** This one directly constrains the search
  page feature and is the reason for the design in section 2.
- The grade is always computed locally.
- A check that cannot run says so, rather than returning a clean pass.
- The verdict never makes a claim about product quality.

## 1. The marketplace registry

### The problem it solves

The list of Amazon storefronts currently exists in four places that can silently disagree:
`host_permissions` and `content_scripts.matches` in `src/manifest.json`, the `ALLOWED_HOSTS`
guard in `package.mjs`, and — implicitly, and worst — the locale tables in
`src/core/language.ts`, which are keyed by language and have no mechanical link to the
storefronts that need them.

That last gap is exactly how the v0.3.0 localisation bug shipped: fourteen storefronts were
added to the manifest, and nothing anywhere required that adding one also meant supplying
its month names, star nouns and date order. The tokenizer stayed English and eleven
storefronts silently produced wrong findings.

`package.mjs`'s guard is also weaker than it looks. `ALLOWED_HOSTS = [/amazon\./]` is an
unanchored regex, so `*://*.amazon.evil.com/*` passes it.

### Design

New module `src/core/marketplaces.ts`, pure and dependency-free, in keeping with the rest of
`src/core`. One entry per storefront:

```ts
export interface Marketplace {
  /** Registrable domain, e.g. 'amazon.co.jp'. Not a match pattern. */
  host: string;
  /** Languages this storefront actually serves, most common first. */
  languages: LanguageCode[];
  /** Day-month order for numeric dates. Informational: numeric dates are still refused. */
  dateOrder: 'dmy' | 'mdy' | 'ymd';
  /** ISO 3166-1 alpha-2, used only for display. */
  region: string;
}
```

The registry's type makes `languages` non-optional and constrains it to `LanguageCode`, so a
storefront cannot be added without naming languages the engine has tables for. Adding
`amazon.com.br` does not compile until `pt` exists in `LanguageCode`, `MONTH_NAMES`,
`STAR_WORDS` and `UNIT_WORDS`. **The bug becomes a type error.**

### Consumers

- `build.mjs` generates `host_permissions` and `content_scripts.matches` from the registry
  when it rewrites the manifest for version. `src/manifest.json` keeps the keys with empty
  arrays and a comment saying they are generated, so the checked-in file never drifts.
- `package.mjs` validates every emitted host against the registry by **exact suffix match**
  on the registrable domain, replacing the unanchored regex. `amazon.evil.com` now fails.
- `src/content/parse.ts` and the new SERP script resolve the current marketplace from
  `location.hostname`.

### Testing

- A test asserts every registry host appears in the generated manifest and vice versa.
- A test asserts the packaging guard **rejects** `amazon.evil.com` and `notamazon.com`.
  Mutation-verified: the guard is reverted to the old regex and the test must go red.
- A test asserts every language named by any registry entry has a non-empty `MONTH_NAMES`
  entry and appears in the star-word list.

## 2. Search-results-page badges

### The constraint, stated plainly

An Amazon search card renders the average star rating and the total rating count. It does
not render the histogram, and it does not render a single review. Winnow's engine requires
at least three readable reviews to grade (`MIN_REVIEWS_TO_GRADE`), and fifty ratings before
it will say anything from a histogram alone.

The only way to obtain reviews for a search card is to fetch its `/dp/` page in the
background, which means crawling Amazon with the user's logged-in session. That risks the
user's Amazon account, and it is a standing non-negotiable. **So Winnow cannot show a real
grade for a product it has not already seen, and this design does not pretend otherwise.**

This is the same discipline the engine already applies to itself. A tool that invented
search-page grades from a star average would be committing precisely the error it exists to
name.

### Design

A second content script, `src/content/serp.ts`, on search and category pages. For each
product card it resolves the ASIN and looks it up in a local cache:

- **Hit** → a small badge showing the grade already computed on that product's own page,
  with the date it was computed.
- **Miss** → a neutral, unobtrusive "not checked" marker. Not a grade, not a warning, not a
  colour that reads as either. Hovering explains that Winnow grades a product when you open
  it, and why it will not guess from a star average.

The cache is populated as a side effect of ordinary use: opening a product page writes its
grade. Coverage therefore starts empty and compounds. That is an honest description of the
feature and the copy will say so rather than overselling day-one density.

Badges are injected into the page, not a shadow root, because they must sit inside Amazon's
grid layout. They carry a dedicated class prefix, a `data-winnow` attribute, and inherit
nothing from Amazon's styles that would let a layout change make them unreadable.

### The cache

New module `src/shared/cache.ts`, backed by `chrome.storage.local`:

- Key: ASIN. Value: grade letter, score, engine version, ISO date.
- **Cap 500 entries, LRU eviction. TTL 90 days.**
- Entries whose `engineVersion` differs from the running build are treated as misses, not
  shown. A grade traces to the logic that produced it; showing a 0.3.0 grade in a 0.5.0
  panel would break that.
- One-click clear in Options, alongside the existing feedback export/delete.
- Disclosed in `PRIVACY.md` and on the options page in plain terms: this is a local record
  of products you have opened, it never leaves the machine, here is how to erase it.

The ASIN is stored in clear. The feedback log hashes ASINs because its purpose is
statistical and it does not need them; the cache's whole function is to match a specific
ASIN on a search page, so hashing would buy nothing a determined local reader could not
undo by hashing the candidate ASINs themselves. Storing it plainly and disclosing it plainly
is the more honest of the two.

### Error handling

- Cache read failure → every card renders "not checked". The feature degrades to absent.
- ASIN not resolvable from a card → no marker at all, rather than a marker that might be
  attached to the wrong product.
- Sponsored and non-product cards are skipped.
- Amazon's search grid re-renders on filter changes; the script uses the same
  `MutationObserver` + deadline discipline the product page script already uses, so it
  cannot defer forever on a continuously mutating page.

### Testing

- A parse test over frozen search-page HTML asserting ASIN extraction and that a card whose
  ASIN cannot be read gets no badge.
- A cache test covering the cap, LRU order, TTL expiry, and engine-version invalidation.
- **A liveness test in the existing style:** one cached product that MUST show its grade, one
  uncached product that MUST show "not checked" — because a badge layer that silently shows
  nothing is indistinguishable from one that found nothing, and that distinction is the
  product.
- An axe pass over the badge states. Badges are the first Winnow UI outside a shadow root,
  so the suite must first prove axe sees them.

## 3. Six additional storefronts

Adding `amazon.com.br`, `amazon.sg`, `amazon.ae`, `amazon.com.tr`, `amazon.ie`,
`amazon.com.be`. Under the registry, each requires its languages to exist first.

- `.sg` and `.ie` are English. No new language work.
- `.com.be` serves French and Dutch, both already present.
- `.com.br` needs **Portuguese**: month names, star nouns (`estrelas`), unit words.
- `.com.tr` needs **Turkish**: month names, star nouns (`yıldız`), and care with the
  dotted/dotless i, which `fold()` must not collapse incorrectly.
- `.ae` needs **Arabic**, and this is the one with a real hazard. Arabic is space-separated
  so the tokenizer handles it, but Eastern Arabic numerals (٠١٢٣٤٥٦٧٨٩) will not match
  `\d`, meaning rating counts, histogram percentages and dates can silently read as zero or
  fail to parse. Silent zeros are exactly the failure mode this project keeps being bitten
  by.

**Decision on Arabic:** add `ar` with month names, star nouns, and an explicit
Eastern-Arabic-numeral normalisation step in `fold()`. If that normalisation cannot be made
to hold up under test, `amazon.ae` ships **without** Arabic support — the storefront is
excluded from the registry rather than added with a locale that produces confident wrong
numbers. Shipping eleven working storefronts and one honest omission beats twelve where one
lies.

`ar` is **not** added to `LANGUAGES_WITH_PHRASE_LISTS`, and neither are `pt` or `tr`. The
incentivised-review phrase lists are judgement calls about idiom; without lists we can stand
behind, `phrasing` reports itself skipped, which is the contract `ReviewSignal.unavailable`
already establishes.

### Testing

- Extend `tests/i18n.test.ts` with a corpus fixture per new language driven through the real
  parser, in the same shape as the existing German fixture.
- A numeral test asserting Eastern Arabic digits parse to the same values as ASCII digits,
  and that a rating count of ٢٣٤ does not read as zero.
- The existing English corpus cases must stay **byte-identical**, as they did through the
  v0.3.0 localisation rework. That equality is the evidence the change touched nothing it
  should not have.

## 4. Firefox build target

### Design

`build.mjs` gains a `--target=chrome|firefox` flag, defaulting to Chrome. The Firefox
manifest differs in three ways:

- `browser_specific_settings.gecko` with a stable extension ID and `strict_min_version`.
- `background` declared with `scripts` alongside `service_worker`, which Firefox accepts and
  Chrome ignores.
- `optional_host_permissions` for loopback, which Firefox treats slightly differently; the
  dev endpoint remains loopback-only and `tests/background.test.ts`'s guarantee is unchanged.

The code needs no `browser.*` shim: Firefox supports the `chrome.*` namespace, and Winnow
already uses promise-returning APIs throughout.

`package.mjs` produces `winnow-<version>-chrome.zip` and `winnow-<version>-firefox.zip`, and
runs the full guard set against **both** manifests. A guard that only checks one target is a
guard with a hole in it.

### Testing

- A test asserting the Firefox manifest passes every packaging guard the Chrome one does,
  including the new exact-suffix host check.
- A test asserting both manifests declare the same permissions and the same host list, so
  the two builds cannot diverge in what they ask for.

## 5. Trust-proof surface

No new mechanism, only accurate statements in three places.

- **Panel** — a line in the existing "What you can check yourself" section pointing at
  Winnow's own permissions, since that section already teaches verification rather than
  asking for trust.
- **Options page** — the permission list, what each is for, and how to check it in
  `chrome://extensions`.
- **Store listing** — description copy stating what Winnow does not request.

### The honesty rule for this section

Comparative claims name **categories, never competitors**. Winnow may state what it requests
and what that means. It may state that some tools in this category request access to
authentication information. It may not name a product, quote an install count, or imply
wrongdoing by a named party — partly because that is a defamation surface, and mostly
because a product whose pitch is calibrated honesty does not get to run the same
comparison-table playbook it is positioned against.

A test asserts no user-facing string matches the names of competing products.

## Risks

- **Badge coverage disappoints.** A user installs for search-page grades and sees "not
  checked" everywhere. Mitigated by copy that leads with how coverage builds, not by
  inventing grades.
- **Amazon's search markup changes.** Same exposure the product parser already has; handled
  the same way, by degrading to no badge rather than a wrong one.
- **Firefox review is slower than Chrome's** and AMO applies its own source-disclosure
  expectations. The build is open source and unminified sources are available, so this is
  process time, not a blocker.
- **Arabic numerals.** Addressed above with an explicit fallback to omitting the storefront.
- **Scope.** Four workstreams in one release. The registry lands first because the other
  three depend on it; each of the rest is independently shippable if the release needs to be
  cut short.

## Success criteria

- Search pages show cached grades and an honest marker otherwise, with a liveness test
  proving both states can occur.
- Twenty storefronts, or nineteen plus a documented reason `amazon.ae` was excluded.
- Chrome and Firefox packages built from one source, both passing identical guards.
- The English corpus fixtures are byte-identical to v0.3.0.
- No new permissions in either manifest. No network requests in either build.
